## 2. SimulationControl.csv

### 2.1 文件作用

[SimulationControl.csv](file:///d:/Wheat/Wheat/docs/reference/DSSAT-PEST/SimulationControl.csv#L1-L7) 决定脚本的运行策略。

当前样例内容：

- DSSAT installation path = `C:/DSSAT46`
- Selection ratio = `0.3`
- Number of model running = `5`
- Number of iteration time = `50`
- Number of randomly generated vectors of genetic coefficients = `10`
- Coefficient of variation = `0.5`

### 2.2 代码中的映射关系

对应代码：

- `DSSAT_path`：[DSSAT_PEST.r:L12-L12](file:///d:/Wheat/Wheat/docs/reference/DSSAT-PEST/DSSAT_PEST.r#L12-L12)
- `Ratio`：[DSSAT_PEST.r:L15-L15](file:///d:/Wheat/Wheat/docs/reference/DSSAT-PEST/DSSAT_PEST.r#L15-L15)
- `pst_factor`：[DSSAT_PEST.r:L16-L16](file:///d:/Wheat/Wheat/docs/reference/DSSAT-PEST/DSSAT_PEST.r#L16-L16)
- `pst_iterations`：[DSSAT_PEST.r:L17-L17](file:///d:/Wheat/Wheat/docs/reference/DSSAT-PEST/DSSAT_PEST.r#L17-L17)
- `Random_No`：[DSSAT_PEST.r:L18-L18](file:///d:/Wheat/Wheat/docs/reference/DSSAT-PEST/DSSAT_PEST.r#L18-L18)
- `CV`：[DSSAT_PEST.r:L19-L19](file:///d:/Wheat/Wheat/docs/reference/DSSAT-PEST/DSSAT_PEST.r#L19-L19)

### 2.3 这些参数分别影响什么

| 字段 | 含义 | 在流程中的作用 |
|---|---|---|
| `DSSAT installation path` | DSSAT 根目录 | 决定 `.CUL`、`DSSBatch.v46`、`DSCSM046.EXE` 去哪里找 |
| `Selection ratio` | 初筛保留比例 | 决定随机试跑后留下多少较优解 |
| `Number of model running` | 实际被脚本当成 `pst_factor` | 写入 `nash.pst` 第 6 行控制参数 |
| `Number of iteration time` | PEST 迭代次数 | 写入 `nash.pst` 第 9 行 |
| `Number of randomly generated vectors of genetic coefficients` | 随机样本数 | 决定粗筛阶段的候选参数数量 |
| `Coefficient of variation` | 误差模型尺度 | 参与适应度函数计算 |

### 2.4 一个重要理解点

文件中的“Number of model running”这个名称并不精准。脚本读取后把它当作 `pst_factor` 使用，而不是“外层循环次数”。

也就是说，CSV 列名和实际代码语义之间有偏差。

### 4.5 观测指标是如何分组的

这是当前项目里最容易看漏、但实际上非常关键的一层设计。

对 `Output` 类型的记录来说，[ParameterOutput.csv](file:///d:/Wheat/Wheat/docs/reference/DSSAT-PEST/ParameterOutput.csv#L9-L30) 中：

- 第 5 列会被脚本读成 `Out_user`
- 第 6 列会被脚本读成 `Out_Mark` 中的“分组编号”

对应代码：

- [DSSAT_PEST.r:L45-L49](file:///d:/Wheat/Wheat/docs/reference/DSSAT-PEST/DSSAT_PEST.r#L45-L49)

也就是说，脚本并不是把每个观测指标都当成完全独立的一项来赋权，而是先按“组”处理。

以当前玉米样例为例，能够在 `Evaluate.ins` 中看到的 8 个指标大致分成以下几组：

| 指标 | 分组编号 | 说明 |
|---|---:|---|
| `ADAP` | 1 | 与发育天数类指标同组 |
| `MDAP` | 1 | 与 `ADAP` 同组 |
| `HWAM` | 2 | 与产量/生物量类中的部分指标同组 |
| `CWAM` | 2 | 与 `HWAM` 同组 |
| `HWUM` | 6 | 单独成组 |
| `H#UM` | 7 | 单独成组 |
| `LAIX` | 4 | 单独成组 |
| `HIAM` | 5 | 单独成组 |

这意味着：

- `ADAP` 和 `MDAP` 不会分别独立定权，而是先作为“第 1 组”
- `HWAM` 和 `CWAM` 也不会分别独立定权，而是作为“第 2 组”
- 其余指标各自作为单独一组参与赋权

### 4.6 分组字段为什么重要

如果没有“分组”这一层，像 `HWAM`、`CWAM` 这种数量级很大的指标会天然主导目标函数，而 `HIAM`、`LAIX` 这种小数量级指标的影响就会被淹没。

加入分组后，脚本的思路变成：

- 先把相近类型的观测指标归到同一组
- 再按该组中最大的观测值来统一缩放

所以第 6 列本质上不是普通备注字段，而是“观测指标权重分组键”。

### 4.7 跨作物观察：这些分组编号并不是玉米特例

继续检查 [ParameterOutput.csv](file:///d:/Wheat/Wheat/docs/reference/DSSAT-PEST/ParameterOutput.csv) 里其他作物后，可以看到一个更有价值的结论：

- 玉米不是单独设计了一套分组号
- 小麦、大豆、水稻等作物基本复用了同一套分组语义
- 这说明“组号”更像是一个跨作物通用的指标分类体系

可以从这些区段直接看到：

- 小麦输出定义：[ParameterOutput.csv:L40-L59](file:///d:/Wheat/Wheat/docs/reference/DSSAT-PEST/ParameterOutput.csv#L40-L59)
- 大豆输出定义：[ParameterOutput.csv:L80-L104](file:///d:/Wheat/Wheat/docs/reference/DSSAT-PEST/ParameterOutput.csv#L80-L104)
- 水稻输出定义：[ParameterOutput.csv:L177-L195](file:///d:/Wheat/Wheat/docs/reference/DSSAT-PEST/ParameterOutput.csv#L177-L195)

从这些样例里，可以总结出一套大致稳定的分组语义：

| 组号 | 常见指标 | 含义 |
|---|---|---|
| `1` | `EDAP`、`ADAP`、`MDAP`、`PD1P`、`PDFP` | 物候/发育时间类 |
| `2` | `HWAM`、`CWAM`、`BWAM`、`VWAM`、`CWAA` | 产量与生物量类 |
| `3` | `GNAM`、`CNAM`、`SNAM`、`CNAA`、`HNAM` | 氮素累积或氮量类 |
| `4` | `LAIX` | 冠层结构类 |
| `5` | `HIAM`、`HN%M`、`VN%M`、`HINM` | 比率、指数、浓度类 |
| `6` | `HWUM` | 单位重类 |
| `7` | `H#AM`、`H#UM`、`H#GM`、`T#AM`、`P#AM` | 计数类 |
| `8` | `PWAM` | 穗/荚/穗部产量类 |
| `9` | `L#SM` | 叶片数类 |
| `10` | `CHTA` | 植株高度类 |
| `11` | `THAM`、`GL%M` | 脱粒率、组分类比例类 |

这组规律对理解项目很重要，因为它说明这里的“分组”不是随便填数字，而是在尝试把同类观测指标放在同一权重层级里。

### 4.8 并不是所有作物都已经完整配置好

继续对比还能看到另一件很关键的事：

- 小麦、大豆、水稻的分组配置比较完整
- 大麦、高粱这类条目里，很多 `Output` 记录的第 5、6 列是空的

可以参考：

- 大麦输出定义：[ParameterOutput.csv:L115-L134](file:///d:/Wheat/Wheat/docs/reference/DSSAT-PEST/ParameterOutput.csv#L115-L134)
- 高粱输出定义：[ParameterOutput.csv:L212-L234](file:///d:/Wheat/Wheat/docs/reference/DSSAT-PEST/ParameterOutput.csv#L212-L234)

这意味着当前仓库中的作物支持度并不一致：

- 有些作物已经进入“可以直接按分组-赋权机制运行”的状态
- 有些作物只是列出了候选输出指标，但权重和分组元数据还没有补齐

所以在实际做参数率定时，不能只看有没有 `Output` 行，还要检查：

- 第 4 列是否启用
- 第 5 列是否给了合理的粗筛权重
- 第 6 列是否给了合理的分组编号

## 5. 三个 CSV 如何联动

可以把三者看成一个三层筛选器：

### 第 1 层：SimulationControl

决定“怎么跑”

### 第 2 层：CropCultivar

决定“跑哪个作物、哪个品种”

### 第 3 层：ParameterOutput

决定“调哪些参数、看哪些输出、边界是多少”

## 6. 数据模型总结

如果用面向对象的方式抽象，这个项目内部隐含的数据对象大概是：

- `RunConfig`
- `TargetCultivar`
- `ParameterDefinition`
- `OutputDefinition`
- `RandomCandidate`
- `PestControlModel`
- `CalibrationResult`

但当前脚本没有显式抽象这些对象，而是把它们都压在矩阵和字符向量里。

这就是为什么脚本可运行，但可维护性一般。
