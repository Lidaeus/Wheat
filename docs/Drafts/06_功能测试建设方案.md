# 功能测试建设方案

## 1. 文档定位

本文件用于回答两个直接问题：

1. 当前项目是否已经具备完整且良好的功能测试体系。
2. 如果没有，后续应如何建设一套能真正支撑 DSSAT 校准研究的功能测试、集成测试与 acceptance 测试体系。

本文不是泛泛而谈的测试宣言，而是一份面向当前仓库结构、当前研究痛点和当前基础设施状态的落地方案，重点覆盖：

- 权重方案是否真的被正确开发并接入
- `Phase 1` / `Phase 2` 的运行链路是否能稳定工作
- 协议输出、结果落盘与后处理是否具有科研可复核性
- 真实 DSSAT 安装环境下是否具备最低可用 acceptance

## 2. 当前检查结论

## 2.1 结论先行

当前项目**有较多测试资产，但还不构成“完整且良好的功能测试体系”**。

更准确地说，当前仓库具备：

- 较强的单元测试与契约测试基础
- 一部分研究层 smoke/质量门禁思想
- 多作物配置解析、固定宽度写回、协议导出等关键模块的测试覆盖

但仍明显缺少：

- 面向权重方案接入正确性的系统功能测试
- 面向 `phase1_runner.py` / `phase1_postprocess.py` 的稳定功能测试
- 面向“从配置 → workspace → run → summary → derived metrics → figure-ready”的端到端可重复功能测试
- 面向真实 DSSAT 安装环境的自动化 acceptance 测试

- 测试体系能够发现一部分回归
- 但关键主链路当前确实存在契约漂移

## 2.4 为什么当前不能算“良好的功能测试”

虽然当前测试数量不少，但它们仍以单元测试、契约测试和局部 smoke 为主，存在五个关键缺口：

1. **没有权重方案矩阵的系统性接入测试**
   - 缺少对 `W0 / W4 / W6 / W8 / W1 / W7` 的统一输入输出校验
   - 缺少“权重方案真的改变了目标构造”的断言

2. **没有 `phase1_runner.py` 的自动化功能测试**
   - 缺少对 `BatchA/B/C/D` 构造、manifest 落盘、workspace 创建、skip-postprocess 行为的稳定检查

3. **没有 `phase1_postprocess.py` 的回归测试**
   - 缺少对 derived metrics、combo summary、平台现象诊断字段的 golden-file 回归检查

4. **没有稳定的离线端到端测试链**
   - 当前缺少一条不依赖真实 DSSAT 安装、但可以完整覆盖研究主链路的 fake acceptance

5. **真实 DSSAT acceptance 没有形成仓库内自动化测试入口**
   - 相关思路在文档中存在，但还没有变成一套可定期运行、可机器判定 pass/fail 的测试资产

## 3. 当前测试体系的结构性判断

建议将当前测试状态判断为：

| 层级 | 当前状态 | 判断 |
| :--- | :--- | :--- |
| 单元测试 | 已建立 | 中等偏强 |
| 契约测试 | 已建立 | 较强 |
| 模块级 smoke | 部分存在 | 中等 |
| 离线功能测试 | 明显不足 | 弱 |
| 批处理工作流测试 | 明显不足 | 弱 |
| 真实 DSSAT acceptance | 文档有思路，自动化不足 | 弱 |

因此，下一步不应只是“再补几个测试函数”，而应把测试体系升级为五层结构。

## 4. 建议的测试体系分层

## 4.1 L0：纯单元测试

目标：

- 保护纯函数、格式化函数、字段映射函数、解析函数

典型对象：

- `crop_registry.py`

- 但不应再误以为 L0 通过就代表研究链路可用

## 4.2 L1：契约测试

目标：

- 保护配置、协议字段、导出表头、manifest、contract report 的稳定性

典型对象：

- JSON 配置解析
- `run_manifest.json`
- `contract_report.json`
- 主矩阵 protocol / quality gate / paper-facing table 的字段契约

说明：

- 当前这层也已有不错基础
- 后续新增字段时，必须同步维护 snapshot/golden contract

## 4.3 L2：离线功能测试

目标：

- 在不依赖真实 DSSAT 安装的前提下，覆盖“配置 → 工作目录 → 运行 → 后处理 → 结果表”的完整链路

典型对象：

## 4.4 L3：研究工作流测试

目标：

- 覆盖主矩阵、批处理、重复运行、后处理汇总、图表长表生成等研究专属流程

典型对象：

- `phase1_postprocess.py`
- 后续 `equifinality_runner.py`
- 后续 `equifinality_postprocess.py`

说明：

- 这层直接关系到论文结果能否可信复现
- 优先级应高于继续增加单元测试数量

## 4.5 L4：真实环境 acceptance

目标：

- 在本机真实 `C:\DSSAT48\` 环境下验证最低可用性

典型对象：

- Wheat live acceptance
- 单作物 live rehearsal
- 真实观测文件解析与真实 case 目录复制

说明：

- 这层不需要每次提交都跑
- 但必须有清晰入口、明确判定标准和落盘产物

## 5. 功能测试建设的核心原则

## 5.1 先覆盖用户当前最痛的风险

当前最重要的风险不是“代码是否优雅”，而是：

- 权重方案是否真的接入
- 协议切换是否真的生效
- 输出表中的字段是否反映了真实运行结果
- 后处理是否可能把不同协议压平为同一结果

因此，功能测试优先级必须围绕：

1. 权重方案
2. 主矩阵协议切换
3. 后处理与 summary 导出
4. 真实环境 acceptance

## 5.2 测试必须能回答科研问题

一个“良好的功能测试”不只回答“代码没报错”，还要回答：

- 不同 `W` 是否真的生成了不同的 loss construction
- 不同 `S` 是否真的生成了不同的 protocol artifacts
- 不同 `G` 是否真的改变了 grouping 边界
- 不同 `O` 是否真的调用了不同求解路径

## 5.3 优先做 deterministic 的离线测试

对于日常回归，优先使用：

- fake DSSAT runner
- 小型固定观测样本
- 固定参数边界
- 稳定 golden outputs

这样才能把问题快速定位为：

- 配置错误
- 权重接入错误
- 后处理错误
- runner 契约漂移

## 7. 第一优先级功能测试设计

## 7.1 权重方案接入测试

建议新增：`test_weight_modes_offline.py`

目标：

- 验证每一种权重方案都被正确识别、正确解析、正确反映到输出 artifacts 中

至少覆盖：

- `W0` 原始恒等
- `W4` 最小-最大归一化
- `W6` 对数变换
- `W8` DSSAT-PEST group-max
- `W1` inverse-variance
- `W7` equal-contribution

每个权重方案至少断言：

1. 协议名与 weight mode 正确写入 manifest / summary
2. 相关 fallback 字段正确写入或为空
3. 关键中间权重或 group maxima 计算结果与预期一致
4. 若该方案应改变目标构造，则生成结果必须与 `W0` 有可观测差异

特别要求：

- 对 `W8` 单独保留 train-only maxima 测试
- 对 `W1` 单独保留方差缺失 fallback 测试
- 对 `W7` 单独保留组贡献平衡逻辑测试

## 7.2 协议矩阵切换测试

建议新增：`test_protocol_matrix_offline.py`

目标：

- 验证 `W × O × S × G` 的关键组合在离线条件下能形成正确的运行计划与协议产物

至少覆盖：

- `W0 × O1 × S1 × G1`
- `W8 × O1 × S2 × G3`
- `W4 × O2 × S2 × G3`
- 一个非法或不兼容组合

每个组合至少断言：

1. `combo_key` 正确
2. grouping/sequence/engine/weight 的归一化名称正确
3. workspace 结构正确
4. contract report 中的 active groups、fallbacks、zero-weight observations 合理

## 7.3 `phase1_runner.py` 功能测试

建议新增：`test_phase1_runner_offline.py`

目标：

- 覆盖 `phase1_runner.py` 的批次构造、会话目录创建、manifest 落盘与 postprocess 调用逻辑

至少覆盖：

1. `BatchA` 是否构造正确组合数
2. `All` 是否同时包含 baseline 和主矩阵
3. `--combo-keys` 是否只筛选指定组合
4. `--train-only` / `--with-validation` 是否正确写入 manifest
5. `--skip-postprocess` 是否跳过后处理

关键断言：

- 生成的 `phase1_run_manifest.json` 字段完整
- `job_count` 与预期一致
- `skipped_crops` 行为正确

## 7.4 `phase1_postprocess.py` 功能测试

5. `param_shift_norm`

当前统一测试已经暴露该模块存在契约漂移，因此建议单独补一组更聚焦的功能测试。

目标：

- 在真实 `C:\DSSAT48\Wheat` 环境下验证项目最低可用性

- 作物：Wheat

## 9. 建议的测试数据与 golden files

功能测试要稳定，必须建设最小 fixture 数据集。

建议准备：

- `mini_case/`
  - 一个极小化 DSSAT case 副本
  - 只保留最少 treatments 和最少必要文件
- `mini_outputs/`
  - 固定的 fake model outputs
- `golden/`
  - `phase1_experiment_summary.tsv`
  - `phase1_derived_metrics.tsv`
  - `phase1_combo_summary.tsv`
  - `contract_report.json`
  - `run_manifest.json`

原则：

- fixture 越小越好
- golden 越稳定越好
- 任何字段变更都必须明确是“有意更新”还是“回归”

## 10. 测试执行分层建议

建议将测试执行分为三档：

## 10.1 快速档

用于日常开发：

- unit
- contract
- offline functional

## 10.2 研究档

用于实验脚本或后处理变更后：

- 快速档全部
- `phase1_runner` / `phase1_postprocess` 离线功能测试
- golden file 回归测试

## 10.3 acceptance 档

用于重要阶段前：

- 研究档全部
- live Wheat acceptance

## 11. 建议的命名与门禁规则

## 11.1 测试命名

- `test_*_offline.py`：离线功能测试
- `test_*_acceptance.py`：真实环境 acceptance
- `test_*_golden.py`：golden file 回归测试

## 11.2 门禁规则

- unit/contract/offline functional 必须全绿才能合入
- acceptance 允许按需手动执行，但失败后不得继续正式批量实验
- 若权重方案接入发生改动，必须跑对应权重测试矩阵

## 12. 第一轮开发优先级

建议按以下顺序建设，而不是同时铺开所有测试：

1. 修复当前已暴露的 `run_model.main()` / `execute_case` 契约漂移
2. 新增 `test_weight_modes_offline.py`
3. 新增 `test_phase1_postprocess_offline.py`
4. 新增 `test_phase1_runner_offline.py`
5. 新增 `test_protocol_matrix_offline.py`
6. 最后增加 `test_live_wheat_acceptance.py`

这样安排的原因是：

- 第 1 步先恢复当前测试入口全绿
- 第 2–4 步直接对准你当前最担心的权重接入和研究主链路
- 第 5 步再做组合层抽象
- 第 6 步最后连接真实 DSSAT 环境

## 13. 验收标准

当满足以下条件时，可认为本项目已具备“基本良好的功能测试体系”：

- [ ] 统一测试入口全绿
- [ ] 所有主权重方案均有离线功能测试
- [ ] `phase1_runner.py` 与 `phase1_postprocess.py` 均有功能测试
- [ ] 至少有一组 golden-file 回归测试保护后处理输出
- [ ] 至少有一条 live Wheat acceptance 可手动运行
- [ ] 权重、分组、顺序、优化器切换都能在测试中被机器断言为真实生效

## 14. 最终建议

当前项目最需要的不是“更多测试数量”，而是**把测试从字段契约层推进到研究功能层**。只有当测试能够直接回答下面这些问题时，它们才真正支撑你的研究：

- 这个权重方案是否真的接进去了
- 这个协议切换是否真的改变了目标构造
- 这个批处理链路是否真的可靠
- 这个结果表是否真的反映了运行差异
- 这个真实 DSSAT 环境是否真的能复现最小闭环

因此，后续功能测试建设应以“权重方案接入 + 主链路离线功能测试 + live Wheat acceptance”作为三条主线推进，而不再停留在单元测试数量增长本身。
