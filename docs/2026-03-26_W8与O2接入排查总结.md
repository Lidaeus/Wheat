## 二、本轮实际做了什么

### 1. 对比 W8 在 sandbox 与 PEST 侧的实现口径

先检查了两个地方：

- `autoresearch_sandbox\eval.py`
- `mvp_pest_mgda\src\build_pest_setup.py`

重点检查的是 **W8 权重怎么计算**。

#### 当时发现的问题

在 `eval.py` 里，W8 的逻辑原本是：

- 先把同一个组里的多个观测指标拼接起来
- 再对拼接后的整体数组取最大绝对值
- 最后取倒数作为组权重

在 `build_pest_setup.py` 里，W8 的逻辑是：

- 先按 DSSAT-PEST 的观测组定义分组
- 每个组单独取组内观测值的最大绝对值
- 最后取倒数作为组权重

这两种写法表面相近，但语义上并不是完全同一件事。  
为了让 sandbox 与 PEST 侧严格一致，我们把 sandbox 改成了 **按组最大值** 的实现。

### 2. 检查 baseline 的比较口径

接着检查 `negative_optimization` 是怎么判定的。

在 `autoresearch_sandbox\auto_evolve.py` 中，原先逻辑是：

- 先运行 `B0 External Baseline`
- 再把每个实验格子的分数拿去和这个 baseline 比
- 如果实验得分更差，就标为 `negative_optimization`

问题在于：这个 baseline 直接采用了 DSSAT 官方参数，也就是：

```text
[9.33, 3.12, 331.4, 12.87, 62.22, 2.215, 86.00]
```

而 sandbox 当前 `project_wheat.json` 给出的参数边界是：

- `P5 >= 550`
- `G2 <= 60`
- `G3 <= 2.1`
- `PHINT >= 95`

这意味着：

- baseline 用的是一组 **边界外参数**
- 但优化器搜索时只能在 **边界内**

于是出现了一个不公平的比较：

- 参考答案允许在场外作答
- 参赛选手只能在场内答题

如果继续用这种口径比较，就很容易把本来已经优化成功的方案误判成 `negative_optimization`。

### 3. 实际验证“边界外 baseline”与“边界内 baseline”的差异

为了验证这个判断，我们实际跑了两种 baseline：

#### 外部 baseline

- 直接使用官方参数，不做边界裁剪

结果：

- 分数：`0.417561`

#### 可行域 baseline

- 先把官方参数裁剪到 sandbox 当前边界内，再运行

裁剪后参数大致变为：

```text
[9.33, 3.12, 550.0, 12.87, 60.0, 2.1, 95.0]
```

结果：

- 分数：`0.469857`

这一步非常关键，因为它证明了：

- 之前的 baseline 确实“占了边界优势”
- 如果按照公平口径比较，W8 的结果并没有想象中那么差

### 4. 接入 O2 = pestpp-ies 的真实执行链路

在 `eval.py` 里，原来 O2 是“设计上有名字，但运行时未实现”。

本轮补上的内容包括：

- 为 IES 增加独立预算参数
  - `ies_noptmax`
  - `ies_num_reals`
  - `ies_subset_size`
- 增加 `pestpp-ies.exe` 的定位逻辑
- 增加 PEST 输入文件构建流程
- 增加分阶段运行时的参数激活控制
- 增加 IES 输出结果解析
  - 从 `ksas_mvp.phi.actual.csv` 中定位最优 realization
  - 从 `ksas_mvp.<iter>.par.csv` 或 `.base.par` 中回收最佳参数

### 5. 修复 O2 初次接入时报错的问题

O2 第一次真正运行时没有直接成功，而是出现了报错：

```text
RuntimeError: No usable observations: A/T files missing or empty after filtering
```

这个报错不是 DSSAT 崩了，而是 **PEST 观测集合被阶段过滤“过滤没了”**。

#### 追查过程

检查后发现：

- IES 分阶段运行时设置了 `PEST_ACTIVE_METRICS`
- 但没有同步设置 `DSSAT_EXTRA_SUMMARY_VARS`

这样会导致：

1. `build_pest_setup.py` 在某些阶段只提取到 T 文件里的 `LAID` 观测
2. A 文件中的 `ADAP / MDAP / CWAM / HWUM` 没有被正确纳入
3. 之后又按阶段指标过滤
4. 最终所有观测权重都被置为 0
5. 于是触发 `No usable observations`

#### 采取的修复

在 `eval.py` 的 O2 运行入口里补充：

```text
DSSAT_EXTRA_SUMMARY_VARS=ADAP,MDAP,CWAM,HWUM
```

修复后，O2 的整条顺序标定链正常跑通。

### 6. 调整 matrix 实验的判定规则

为了避免后续 matrix 结果再次出现误判，我们在 `auto_evolve.py` 中做了两件事：

1. 保留原来的 `B0 External Baseline`
   - 用于复现 DSSAT 官方参数的原始参考表现
2. 新增 `B0 Feasible Sandbox Baseline`
   - 用于作为 sandbox 内部实验的公平比较基线

然后把 `negative_optimization` 的判定改为：

- 不再对照 `External Baseline`
- 改为对照 `Feasible Sandbox Baseline`

## 五、为什么之前会误判为 negative_optimization

这一部分是整轮排查里最关键的逻辑。

### 结论先说

**W8 不是失效了，而是比较基线不公平。**

### 更直白的解释

之前系统是在做下面这件事：

- baseline：允许使用一组超出当前 sandbox 边界的参数
- 优化器：只能在当前 sandbox 规定的边界内搜索
- 然后把两者直接比较

这会带来一个自然后果：

- 即使优化器已经在“允许范围内”找到了很好的结果
- 它仍然可能输给一组“本来就不允许进入搜索空间”的参数

所以原来的 `negative_optimization` 里混入了大量“口径问题”，而不一定是真实的算法退化。

---

## 六、如何理解“可行域 baseline”

用户最容易困惑的就是这一点，所以单独解释。

### 可行域是什么意思

“可行域”就是 **当前优化器被允许搜索的参数范围**。

在这次 Wheat sandbox 里，可行域由 `project_wheat.json` 的 bounds 决定。

例如：

- `P5` 不允许低于 `550`
- `PHINT` 不允许低于 `95`

### 为什么需要可行域 baseline

如果你要判断“优化器有没有变差”，最公平的做法应该是：

- 让 baseline 也待在同一个搜索范围内
- 再比较两者谁更好

否则你比较的其实不是：

- “算法 A 和算法 B 谁更强”

而是：

- “一个受限优化器”和“一个不受限参考参数”谁更强

这两个问题不是同一个问题。

### 这一轮的直观例子

原始官方参数里有：

- `P5 = 331.4`
- `PHINT = 86.0`

但 sandbox 规定：

- `P5 >= 550`
- `PHINT >= 95`

所以这组参数在 sandbox 实验里其实是“超界”的。

把它裁进边界以后，baseline 分数从：

- `0.417561`

变成：

- `0.469857`

这就说明原来那条 baseline 的确享受了“边界外优势”。

## 七、这轮分析最终推导出的结论

### 结论 1

W8 在 sandbox 中出现 `negative_optimization`，主因不是 W8 本身无效，而是：

- baseline 比较口径不公平

### 结论 2

W8 的 sandbox 实现与 PEST 侧实现原本存在轻微口径偏差，已经对齐为：

- 按观测组最大值计算权重

### 结论 3

O2 `pestpp-ies` 之前确实没有真正接入 sandbox 运行链，现在已经接通并可实跑。

### 结论 4

在当前测试设置下：

- W8 + O1 的结果已经优于可行域 baseline
- W8 + O2 的结果进一步提升到 `0.370379`

### 结论 5

因此，`DSSAT-PEST` 中“W8 优于官方参数”的经验结论，与 sandbox 当前复盘结果是可以同时成立的，并不矛盾。

它们之前看起来矛盾，只是因为 sandbox 的 baseline 选取方式不公平。
